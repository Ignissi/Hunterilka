# Проверка установки и сценариев

## PostgreSQL 16 и Docker

В `docker-compose.yml` описан PostgreSQL 16 с постоянным томом. После запуска контейнера проверяются рабочая и отдельная тестовая базы:

```bash
python -m scripts.check_runtime
HUNTERILKA_REQUIRE_DB=1 python -m unittest discover -s tests -v
```

При недоступной БД этот режим завершает проверку ошибкой. CI использует PostgreSQL 16 и тот же обязательный режим SQL-тестов. Тесты очищают только выбранную тестовую БД; `HUNTERILKA_TEST_DB` нельзя направлять на рабочую базу.

## Проверяемые сценарии

- Признаки операции используют предшествующую историю; равное время обрабатывается общей группой.
- Скользящее окно удаляет старые события.
- Сбой во время записи откатывает операции, случаи и позицию обработки вместе.
- Продолжение восстанавливает граф, оценки и сохранённые признаки.
- Повтор последней сохранённой группы не создаёт дубликатов; изменение её содержания обнаруживается.
- Решения специалиста и версии случаев сохраняются.
- Новый вход принимает операции за произвольные даты без меток и обучающего manifest.
- Файл подтверждается после записи в БД; остановка между записью и подтверждением не дублирует результат.
- Обновление схемы сохраняет существующую позицию потока.
- Генерация отчёта сохраняет метрики всего test и дополнительные временные срезы.

## Локальный ML-эксперимент

Полный расчёт на Linux с Python 3.12 и GPU-обучением CatBoost завершён: обработано 4 930 063 операций IBM HI-Small, модели и отчёты сохранены. Фактические численные результаты приведены в [results.md](results.md).

Проверка установки и оценка ML решают разные задачи: SQL-тесты проверяют сохранение и восстановление, размеченная история — качество моделей. Измерения производительности при многопользовательской нагрузке в этих результатах не представлены.
